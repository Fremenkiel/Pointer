# Design review, 2026-10-17

This document reviews the design before the first line of code. It has two parts. Part A lists design findings. If the code follows the documents as written, each finding does damage, and the list is ranked by that damage. Part B lists the result of the source review of [research.md](research.md). Each finding names the document that it affects and a recommendation. The product owner decides each recommendation. The new open questions are D-26 to D-33 in [decisions.md](decisions.md).

Severity levels:

- S1: the app loses data, or the app is slower than the hardware allows, or memory grows without a bound.
- S2: a visible defect, or a design that blocks a later feature that the documents promise.
- S3: an error in a document, a number, or a source. The code does not suffer.

## Part A: design findings

### A-01 (S1) The stored stroke is the subdivided polyline, not the samples

Where: [architecture.md](architecture.md) 4.3, [data-model.md](data-model.md) 7.4, `Limits.maxPointsPerStroke`.

The design subdivides each stroke until no segment is longer than 0.5 canvas points, and stores the subdivided points. Apple Pencil gives 240 samples per second. The table shows what the rule does at normal pen speeds (1 canvas point is 0.156 mm at zoom 1):

| Pen speed | Canvas points per second | Stored points per second | Inflation over 240 Hz | Time to reach 16,384 points |
|---|---|---|---|---|
| 5 cm/s (slow writing) | 321 | 642 | 2.7 | 25 s |
| 15 cm/s (normal writing) | 963 | 1,925 | 8.0 | 8.5 s |
| 30 cm/s (fast sketch line) | 1,925 | 3,850 | 16.0 | 4.3 s |
| 50 cm/s (fast arrow) | 3,209 | 6,417 | 26.7 | 2.6 s |

Effects:

1. The limit comment "about 68 s of pencil input" is wrong. A fast line ends after 3 to 4 seconds and a new stroke starts.
2. Storage, memory, load time, and GPU work grow 3 to 27 times.
3. The stored data depends on a rendering tolerance. A change of the tolerance changes every stored stroke.
4. The budget "20,000 strokes of 300 points" assumes 300 samples per stroke. With subdivision, a stroke of 300 samples becomes 1,000 to 8,000 points.

Recommendation: store the filtered samples, 240 per second at most. Define the shared geometry as the curve through the samples (centripetal Catmull-Rom), not as a polyline. The renderer flattens the curve to a screen tolerance each time it builds a draw list. The PDF exporter writes the same curve as cubic Bézier segments, which a Catmull-Rom spline converts to exactly. FEEL-03 still holds, because the live stroke and the final stroke run through the same filter and the same curve code. Keep `maxPointsPerStroke = 16,384` and fix the comment to "68 s at 240 Hz".

### A-02 (S1) The save rule has no upper bound and breaks STO-06

Where: [storage.md](storage.md) 4, step 4.

The repository writes "one second after the last change". While the user draws without a pause, the last change moves forward and the write never runs. A 10-minute sketch session can lose 10 minutes of ink on a crash. STO-06 allows 2 seconds.

Recommendation: throttle, do not debounce. If the pending set is not empty and the last write is older than 1 second, write. If the pencil lifts and the last write is older than 1 second, write. Add an automated test to M3: draw for 10 seconds without a pause, kill the process, reopen, and expect at most 2 seconds of lost ink.

### A-03 (S1) Value copies of `CanvasContent` copy the whole canvas on the main actor

Where: [data-model.md](data-model.md) 8, [architecture.md](architecture.md) 9 and 11.

`CanvasContent` holds dictionaries with up to 200,000 strokes. Swift copies a dictionary only on the first write after a copy exists (copy on write). The design hands value copies of the content to the renderer, the exporter, and the repository. Each time a copy exists and the main actor appends a stroke, Swift copies the whole dictionary: 200,000 entries, each with a retain and a release of an array. That takes milliseconds on the main actor at every pencil lift, which drops a frame.

Recommendation:

1. Only the canvas controller holds `CanvasContent`. The renderer receives deltas (the IDs of added and erased strokes) and keeps its own GPU state. The repository receives changed rows, as section 4 of storage.md already says.
2. The exporter takes a copy. That is fine, because export is rare and the user starts it.
3. Make the point storage of a stroke an immutable reference type, for example `final class InkPoints: Sendable` over a `[InkPoint]`. A copy of a `Stroke` or a dictionary then costs one retain, never a copy of the points. The Model package stays pure.

### A-04 (S1) Pan and zoom have no level of detail and no cache

Where: [architecture.md](architecture.md) 5.2, 5.3, 5.6, 12. [plan.md](plan.md) M2 acceptance 2.

While the camera moves, the design draws every visible capsule from the GPU buffers. The arithmetic for a canvas that is fully visible at zoom 0.25:

| Canvas | Capsules per frame | Vertices per frame | Vertices per second at 120 Hz |
|---|---|---|---|
| 20,000 strokes of 300 points | 6 M | 24 M | 2.9 G |
| 200,000 strokes of 300 points (the limit) | 60 M | 240 M | 29 G |

An iPad GPU does not do 29 G vertices per second. At zoom 0.25 most capsules are smaller than one pixel, so this work draws nothing that the user sees. The M2 acceptance test runs at 20,000 strokes, so the design passes M2 and fails at the limit that the documents allow.

The spatial grid number is also wrong. A 13-inch iPad Pro has 1,376 by 1,032 points. At zoom 0.25 the viewport covers 5,504 by 4,128 canvas points. That is 11 by 9 cells, and up to 120 cells in the worst case, not 40.

Recommendation:

1. While the camera moves, show the committed texture, translated and scaled. Render the committed texture with a margin around the viewport, so a pan of less than the margin needs no new content pass. When the camera settles, redraw the content, or redraw it in budgeted chunks per frame.
2. Give each stroke a level of detail: a precomputed stride per zoom band that keeps points at least 0.5 screen pixels apart. At zoom 0.25 a 300-point stroke becomes about 75 capsules.
3. Add an acceptance test at the limit: 200,000 strokes pan and zoom at 120 Hz without a dropped frame.

### A-05 (S1) Points live twice, and GPU buffers churn at the viewport edge

Where: [architecture.md](architecture.md) 5.3.

The design keeps `[InkPoint]` arrays on the CPU and builds a separate `CapsuleInstance` buffer (20 bytes per segment) per stroke on the GPU. For 20,000 strokes of 300 points that is 96 MB plus 120 MB. When a stroke leaves the viewport plus one screen, the renderer frees its buffer. When the stroke returns, the renderer builds the buffer again. A pan back and forth at that edge rebuilds buffers every frame.

Apple GPUs share memory with the CPU. One copy is enough.

Recommendation:

1. Keep all points of a canvas in one arena `MTLBuffer` with `.storageModeShared`, managed by a slab allocator. A stroke owns a range in the arena. The load path copies each point BLOB from SQLite straight into the arena.
2. The vertex shader reads two consecutive points per instance and builds the capsule itself (vertex pulling). No `CapsuleInstance` array exists.
3. Per frame, the CPU writes one small draw list for the visible strokes: first point, count, and the stroke origin minus the camera center as `Float`. One instanced draw call reads it. This also makes "one draw call" true, which the current design does not achieve with one buffer per stroke.
4. Evict by a byte budget with least-recently-used order and a hysteresis margin, never by viewport distance.

### A-06 (S2) Anti-aliased capsules need a blend rule or the joints show notches

Where: [architecture.md](architecture.md) 5.3.

The design says that opaque white ink needs no blending. The fragment shader gives each capsule an anti-aliased edge. Where two capsules of one stroke overlap, the edge pixels of the later capsule (gray) overwrite the interior pixels of the earlier capsule (white). The joints then show dark notches.

Recommendation: because ink is white on black, `MTLBlendOperation.max` is exact. Set the blend operation to `max` for the ink pipeline, or draw coverage into an R8 texture and composite once. State the pipeline state in section 5.3 and add a snapshot test of a tight zigzag stroke. See forum thread 778149 and the Blender Grease Pencil stencil fix for the same problem.

### A-07 (S1) Undo history and tombstones duplicate points in memory

Where: [architecture.md](architecture.md) 8, [data-model.md](data-model.md) 5, 7.5, 8. [storage.md](storage.md) 5, step 5.

Three related problems:

1. Commands hold strokes. 500 steps of `AddStroke` with 16,384 points each hold 131 MB in the worst case. `EraseStrokes` holds the removed stroke and the new parts.
2. The read path loads all `stroke_erase` rows and all erased strokes of a canvas. Erased strokes of past sessions then live in memory and in the arena, although no undo can ever need them. Section 5 of data-model.md says that the repository is the only place that filters tombstones, and section 8 then gives `CanvasContent` an `erased` dictionary. The two statements conflict.
3. No garbage collection exists for erased strokes. A `stroke_erase` row keeps its stroke row forever. Cards get a 30-day rule (D-18), strokes get none.

Recommendation: commands hold IDs only. An undo of `AddStroke` marks the stroke as erased in memory, it does not remove it, so the points live once. The read path loads live strokes only (`LEFT JOIN stroke_erase ... WHERE erased IS NULL`). The in-memory `erased` set holds the erasures of this session only. Apply the 30-day rule of D-18 to erased strokes too.

### A-08 (S1) The eraser writes a new stroke row at every sample

Where: [architecture.md](architecture.md) 4.4.

The eraser runs a hit test and a split on each pencil sample, 240 times per second. A sweep through a hatched area splits a stroke, then splits one of the parts at the next sample, and so on. Each split creates stroke rows with point BLOBs, tombstones, and GPU buffer builds, 240 times per second. The database fills with parts that lived for 4 milliseconds.

Recommendation: during the gesture, keep a mask per touched stroke (the removed point intervals) in memory and render with the mask. At pencil lift, compute the final parts once and emit one `EraseStrokes` command. The undo step stays one gesture, as the design already wants.

### A-09 (S2) An undo of an erase deletes a row, which breaks the change-upload plan

Where: [data-model.md](data-model.md) 7.5 and 11, [storage.md](storage.md) 8.

Section 11 promises that a later backup can find all changes after a clock value. An undo of an erase removes the `stroke_erase` row. A removed row has no clock value, so the change file never learns that the stroke is live again.

Recommendation: never delete a row. Give `stroke_erase` the same `modified` and `is_deleted` columns as the other tables, or an `undone` clock column. An undo sets the flag.

### A-10 (S1) A text box texture does not fit in a Metal texture

Where: [architecture.md](architecture.md) 5.4, 7, 10 (`maxTextLength`).

The limit allows 100,000 characters per text box. In SF Mono at 17 points and 640 points of width, that is 62 columns and about 1,600 lines, or 33,000 canvas points of height. The texture at zoom 1 on a 2x display is 1,280 by 65,800 pixels and 337 MB. At zoom 8 it is 10,240 by 526,000 pixels. Apple GPU families 3 to 9 allow 16,384 pixels per side (Metal Feature Set Tables, 2026-05-21). The cache limit of 256 textures has no byte budget, so 256 large textures exhaust memory.

Recommendation: do not render one texture per text box. SF Mono is monospaced. Build one glyph atlas per power-of-two scale and draw each text box as one quad per character from the atlas. The cache is then a few atlases of a few megabytes, and the size of a text box does not matter. Lower `maxTextLength` to 10,000 for version 1 in any case. Give every cache a byte budget, not a count.

### A-11 (S2) Open-time work: previews one level deep and garbage collection at launch

Where: [storage.md](storage.md) 5, step 6. [decisions.md](decisions.md) D-18. [architecture.md](architecture.md) 12.

To open a canvas, the read path loads the child canvas of every visible card for its preview. A canvas with 500 cards then runs 500 queries and 500 render passes before the first frame. D-18 also runs the 30-day removal of card subtrees at launch. Both compete with the 300 ms open budget.

Recommendation: render previews lazily with a per-frame budget, for example two previews per frame. Store the preview bitmap in `Caches/previews`. Invalidate it by the largest `modified` value of the child canvas. Run garbage collection after the first frame, inside the repository actor, with a bound on rows per launch, followed by `PRAGMA incremental_vacuum`.

### A-12 (S1) Snapshots at the background transition can leave a corrupt file

Where: [storage.md](storage.md) 7.1, 7.2.

SQLite documents two facts about `VACUUM INTO`. An interrupted run leaves an output file that is "incomplete and corrupt" in the words of the SQLite manual. If the target file exists, the command fails. iOS gives about 30 seconds of background time (Apple DTS, forum thread 85066), and that number changed before. A large library at the background transition can hit that limit, and the user then sees a corrupt file in `Backups/`. The repository actor also stops all saves while `VACUUM INTO` runs.

Recommendation: write the snapshot to a temporary file in `tmp/`, then rename it into `Backups/` after success. Delete stale temporary files at launch. Run the snapshot on a second, read-only connection in its own actor, so saves continue (WAL allows one writer and many readers). Prefer the first idle moment after 24 hours while the app is active over the background transition. Keep `synchronous = NORMAL`, because SQLite then syncs the output file.

### A-13 (S2) The repository actor blocks a thread of the shared pool

Where: [architecture.md](architecture.md) 11.

A Swift actor runs on the cooperative thread pool, which has one thread per core. SQLite calls block that thread for the whole call. A snapshot of several seconds or a slow write then removes a thread from the pool that the whole app shares.

Recommendation: give `SQLiteLibraryRepository` a custom serial executor backed by a `DispatchSerialQueue` (SE-0392, Swift 5.9). The minimum platform iPadOS 26 avoids the iOS 17 problems with this feature. Blocking SQLite calls then run on their own thread.

### A-14 (S2) Palm touches reach the finger gestures

Where: [architecture.md](architecture.md) 4.1, 4.7.

Finger gestures accept all `.direct` touches. iPadOS suppresses most palm touches while the pencil is near the screen, but not all. A palm that passes through pans the canvas while the user writes.

Recommendation: ignore new `.direct` touches that begin while a pencil touch is active and for about 150 ms after it ends. Treat a touch with a large `majorRadius` as a palm. Honor `UIPencilInteraction.prefersPencilOnlyDrawing`. Add a device test to M2.

### A-15 (S2) The frame budget ignores the cost of low-latency dispatch

Where: [architecture.md](architecture.md) 5.1 and 12.

Apple documents that low-latency pencil events "dispatch in the middle of a UI update". Apple adds that this "gives an app half the amount of time to handle them as standard events". At 120 Hz the frame is 8.3 ms, so input handling plus command encoding has about 4 ms. The budget table lists 4 ms CPU and 4 ms GPU as two separate budgets. The 4 ms CPU value is the whole budget.

Apple also documents `presentsWithTransaction` as a tool to synchronize Metal content with Core Animation, not as a latency tool. It makes the main thread wait in `waitUntilScheduled()`. Apple states no requirement that immediate presentation needs it. Forum thread 797083 used a plain `UIView` without Metal and has no replies, so it says nothing about a Metal layer.

Recommendation: set the CPU budget for the low-latency phase to 3 ms and measure it in M1. Make `presentsWithTransaction` a variable of the M1 test, not a fixed choice, and measure both settings.

### A-16 (S2) Random UUIDs scatter the primary key index

Where: [data-model.md](data-model.md) 3.

RFC 9562 states that "UUID versions that are not time ordered, such as UUIDv4 ... have poor database-index locality". A `BLOB PRIMARY KEY` in SQLite is a unique index next to the rowid table. Random keys spread each insert over the whole index. Time-ordered keys (UUIDv7) land at the end.

Recommendation: generate UUIDv7 in `EntityID.new()`. Foundation has no UUIDv7 function, so the Model package makes one from the wall clock and random bytes. The change costs 20 lines now and a migration later.

### A-17 (S2) The PencilKit fallback of D-02 does not work for Pointer

Where: [decisions.md](decisions.md) D-02, [research.md](research.md) 4.1.

Apple confirmed in March 2026 that `PKCanvasView` flickers at zoom scales other than 1x and that no app-level workaround exists. Pointer zooms from 0.25 to 8. The fallback also needs one `PKCanvasView` per visible card. If the custom engine fails M1, the fallback fails too.

Recommendation: define the real fallback now. Options: accept the measured latency of the custom engine, or use PencilKit for input capture only and keep the custom renderer. Record the decision in D-33.

### A-18 (S3) The clock value in `device.json` can go backwards after a crash

Where: [data-model.md](data-model.md) 4 and 10.

The last clock value lives in `device.json`. The app writes that file less often than the database. After a crash, a system clock that moved backwards then gives a new value below a stored one.

Recommendation: store the last clock value in the `library` table in the same transaction as the rows.

### A-19 (S3) Edited text is blurry at high zoom

Where: [architecture.md](architecture.md) 5.4 and 7. [plan.md](plan.md) M5.

A `UITextView` under a scale transform renders at its own scale, then the layer scales the bitmap. At zoom 4 the text is blurry. At zoom 8 a raised `contentScaleFactor` makes a very large backing store.

Recommendation: set the font size to 17 times the zoom and use no transform, or raise `contentScaleFactor` and limit editing to zoom 4 or below. Extend the M5 test to zoom 8.

### A-20 (S3) `PERF-01` is not enforceable as written

Where: [code-of-code.md](code-of-code.md) 3.8.

`coalescedTouches(for:)` returns a new array from UIKit at every event. The rule "no allocation in the per-sample path" fails on the first line.

Recommendation: rewrite the rule as "no allocation by Pointer code in these paths. Buffers are allocated once and reused. Allocations inside UIKit and Metal are accepted." Enforce it with an allocation count from Instruments on the engine in isolation, not with `XCTMemoryMetric` alone.

### A-21 (S3) Document errors

1. [architecture.md](architecture.md) 2 and 6.1: `Camera` appears in `CanvasFeature` text and in `DeviceState` (Model). Place it in `Geometry` or `Model` and say so.
2. [code-of-code.md](code-of-code.md) `ARCH-03`: Tier A packages import only Foundation, CryptoKit, and os, but `Persistence` is Tier A and imports SQLite3. Add the exception to the rule.
3. [research.md](research.md) 4.2: the Float step at 1,000,000 is 0.0625, not 0.125. The value 0.125 applies from 1,048,576.
4. [plan.md](plan.md) M3: the acceptance list is numbered 1, 2, 4, 3.
5. [architecture.md](architecture.md) 4.2: the 1€ filter start value `beta = 0.007` is not the author's default. The author's reference code uses `beta = 0` and the author's page says to start with 0.001 or 0.0001. The value is a tuning start either way.
6. [storage.md](storage.md) 3.1: `auto_vacuum = INCREMENTAL` does nothing unless the code also runs `PRAGMA incremental_vacuum`. Either add that call to garbage collection (A-11) or drop the pragma.
7. [storage.md](storage.md) 7.5: if the destination uses WAL and the page sizes differ, `sqlite3_backup_step` returns `SQLITE_READONLY`. Pin the page size in both the live database and the snapshot. After a restore, run the migrations, because the snapshot can carry an older `user_version`. The picked file also needs `startAccessingSecurityScopedResource()`.
8. [storage.md](storage.md) 7.1: snapshot names use minutes. Two snapshots in one minute collide. Add seconds.
9. [architecture.md](architecture.md) 5.2: say that the end of a stroke draws only the new stroke into the committed texture. A full redraw at every pencil lift costs a frame on a large canvas.
