# Code review after M8, 2026-10-24

This review covers the whole code base at commit 79b2f6b, the close of M8. It looks at memory, allocations, correctness, and the match between the documents and the code. It also says what M9 needs before it can start.

Seven reviewers read one area each: Rendering (two parts), CanvasFeature, Persistence, Model with Geometry and InkEngine, Export with WorkspaceFeature, the app target, and the tools, and the documents. Each finding below has a status:

- Fixed: the fix is on branch `review-m8`, with a test that fails before the fix, or with a measure on the iPad.
- Rejected: a benchmark showed no gain.
- Open: read in the code, not fixed. The section gives the reason.

All device measures come from the iPad Pro 11-inch (M4), in Release. Each run has a result bundle under `.build/Runs` with the prefix `R-`.

## 1. Fixed

### 1.1 The text edit laid out its text on each frame of the zoom spring

`CanvasViewController.applyCamera` used the scale transform of D-85 only while the pinch recognizer ran. After a pinch past a zoom limit, the spring back changed the zoom on each frame. `TextEditView.layOut` then built the attributes and laid out the whole text again on each frame.

| Build | Spring frames | Pointer allocations per frame | Slowest frame |
|---|---|---|---|
| Before (984 characters) | 44 | 139 to 141 | 14.57 ms |
| After | 44 | 0 before the last frame | not over 8.3 ms in the run |

The spring now counts as a part of the pinch. The edit view keeps its scale transform until the spring stops. Then it lays out once. architecture.md section 5.4 states this rule. `TextEditFrameAllocationTests.testSpringFramesWithALongText` fails with the old code (`R-spring-inject.xcresult`).

The allocation tracer of the test also had a gap. It counted each image outside its two lists as Pointer code. UIFoundation (the TextKit of `UITextView`), `libc++abi`, and `libsystem_blocks` thus counted as Pointer, about 31 allocations per frame of a scaled text view. The tracer now walks past these images to the caller.

### 1.2 A damaged card row kept a read open on the write connection

`readParents` of `validPath` threw on a card row that did not decode and skipped the `reset` of its statement. The open read pinned the WAL file for the rest of the session. Each passive checkpoint then copied nothing, and the WAL grew without a bound. `readRows` had the same gap after a failed step. Both reads now reset in a `defer`, as `DeviceStateStore` does. `RepositoryCheckpointTests.damagedPathCardLeavesNoRead` fails before the fix.

### 1.3 Metal read 24 bytes of a 20-byte value

`setVertexValue` and `setFragmentValue` passed `MemoryLayout.size`. `CardPreviewUniforms` ends in a `float` after two `float2` values, so Swift gives it a size of 20 bytes and Metal reads 24. A run with Metal API validation on the iPad stopped at the card preview draw: "has space for 20 bytes, but argument has a length(24)" (`R-validation-1.xcresult`). The helpers now pass the stride with zeroed padding. A full run of `PointerDeviceTests` with validation found two more errors, both in the bare passes of two allocation tests, which drew without bound buffers. They now bind a zero buffer, and the render suites pass with validation (`R-validation-3.xcresult`).

No device run used API validation before. A check of validation in each milestone is item 3.4.

### 1.4 The eraser could stop the app

The scan of `StrokeHitTest` can close a covered range at a parameter and open the next range at the same parameter. The cause is a curve point at exactly the reach of two eraser legs, with covered neighbors. The release precondition of `StrokeSplitter.shapes` then stopped the app. A range that opens where the last one ends now opens the last one again, because the free point has no length. `StrokeSplitterTests.touchingRanges` crashed before the fix, with eraser legs at x = 30 and x = 70.

### 1.5 The layer check missed imports with an access level

Swift 6 allows `internal import Persistence` (SE-0409). `Scripts/check-layers.swift` did not match it, so such an import passed ARCH-02. The new fixture `layers-access-import` fails before the fix.

### 1.6 Test isolation

`OnScreenCanvas.open` and `transition` threw at a timeout with the canvas still on the shared test window, with its renderer and the D-56 content. Each later memory or frame test of the run measured them too. A helper now closes each canvas that the measure left, on each exit (TEST-04).

### 1.7 A snapshot test deleted a library that was still open

`SnapshotPerformanceTests` deleted its folder while the repository and its checkpointer still held the files. SQLite logged "vnode unlinked while in use", and the last checkpoint failed with a disk I/O error during the next suite. Its work counted in the process heap of `StrokeStoreMemoryTests`. That test measured 80.7 MB against its limit of 75 MB in two full runs, and 65.1 to 70.1 MB alone (`R-full-1.xcresult`, `R-store-alone-1.xcresult`). A full run without the new preview test passed with 65.1 MB, because the order of the suites decides the overlap (`R-full-skip-1.xcresult`). The tests now wait for the last checkpoint and release the repository before the delete. The next full run measured 65.1 MB (`R-full-2.xcresult`).

### 1.8 Documents and dependencies

- README: the status after M8.
- architecture.md section 11: `WALCheckpointer` is a fourth actor with its own connection (D-146).
- architecture.md section 5.2: the committed texture has twice the drawable size. The renderer draws no selection outline, and the product has no selection.
- plan.md: the M8 fix plan fixed two items of the M10 list, `AppMessageTests` and the slow save after a snapshot. They are no longer in the list.
- `Rendering` and `Export` declared `InkEngine` but import nothing from it. Both manifests and the table of architecture.md section 3 no longer list it.
- Comments: a slab is 128 KB, not 256 KB. A card opens on a tap (D-115), not on a double tap.

## 2. Rejected

### 2.1 A cheaper path of each stroke in the PDF

The export builds a `[Point]` array, a `StrokeCurve`, and a `CGMutablePath` for each stroke, and `addPath` copies the path into the context. A temporary test compared three variants on the 20,000 strokes of D-56, in 3 alternating rounds in one process (`R-bench-1.xcresult`):

| Variant | Round 1 | Round 2 | Round 3 |
|---|---|---|---|
| Path, as now | 6.544 s | 6.715 s | 6.675 s |
| Curves straight into the context | 6.629 s | 6.654 s | 6.658 s |
| Into the context, with one reused point buffer | 6.702 s | 6.662 s | 6.702 s |

The differences are smaller than the differences between rounds. Core Graphics spends the time in the write of the PDF. The code stays as it is.

## 3. Open findings

Each item names the place, the fault, and the reason why it is not fixed here.

### 3.1 Needs a decision of the product owner

Section 4 lists these as D-148 to D-161.

1. `EraseStrokes.revert` refuses an undo above `Limits.maxStrokesPerCanvas`, but `apply` allows `maxStrokesAfterErase` (D-73). At 200,000 strokes, an erase that cuts strokes and a second erase that removes one whole stroke give 200,001 strokes. The undo of the second erase then fails with `strokeLimitReached`, and each later undo tries the same step. The doc comment of `revert` states the old rule on purpose. D-159 holds the question.
2. `SpatialGrid.insert` and `remove` loop over each cell of the bounds of an item, with only the cell clamp of 2^30 as a bound (FLOW-03). An item 10,000,000 points wide took 96 s and 381 million cells on the Mac. The pen cannot make such an item. A damaged row or a restored snapshot can, because `Card.init` and the point reader check only that values are finite. D-158 holds the question.
3. `TextEditing.hitTest` breaks a tie of two equal sort keys with the order of a `Dictionary`, which changes with each launch. data-model.md section 6 says that the record ID breaks the tie, as `card(at:)` does. Equal keys come from the fallback of a key that needs a rebalance.
4. A stroke at the stroke limit disappears with a log line only (`LiveStrokeHandoff.swift:68`). architecture.md section 10 asks for a short message. The comment there names M10, but the M10 list does not hold it. It needs a string in the String Catalog.
5. The undo histories hold at most 16,000,000 points (D-76). But the history of the shown canvas is outside `CanvasSessions`, so the worst case is about 20,000,000 points. The document or the code changes.

### 3.2 Correctness, fix with a test in M9 or M10

1. The repository has no close operation. Up to 14 more device test cases delete a library folder while SQLite holds its files, most of them through `D56Library.remove()`, and 2 background checkpoints of a full run fail after such a delete. A close that waits for the checkpointer and ends all connections fixes them, and the restore of M9 needs the same close (D-148).
2. A failed `SQLiteLibraryRepository.open` leaves `connection` and `statements` set. `send` and `saveNow` then still write, and `open` cannot run again. A damaged `lastTimestamp` row is one way there. M9 needs a clean close and reopen for the restore, so this belongs to M9.
3. The background save keeps one shared `backgroundTask`. At its end, each save task ends the task that the property holds at that time. After a background, a foreground, and a second background within one save, the first task ends the second one. The fix gives each save its own identifier. The window is the time of one save, a few milliseconds.
4. The camera wait of `RenderEngine` signals the semaphore after the lock. If the wait times out in that gap, a late signal stays, and the next frame does not wait. The window is a few instructions wide. Signaling inside the lock closes it. No deterministic test can show it, so the fix needs the agreement of the product owner (TEST-03).
5. If 16 requests wait, `PreviewAtlas.want` drops a card in silence. Only a build or a redraw asks again, so a card can stay without a preview at rest. No test has more than 16 cards that need a preview.
6. A frozen frame of an open does not mark the preview slot of the opened card as used. A full preview atlas can evict that slot during the flight.
7. `WorkspaceSelectorModel.rename` writes to an index that it found before an `await`. The repository methods are synchronous on an actor. A delete thus comes first only if the actor reorders its queue. No test can make that order.
8. The three commits at launch (creation rows, tombstones, `incremental_vacuum`) do not ask for a checkpoint. A large cleanup leaves a large WAL until the first save.
9. The busy check of `checkpointPassive` compares the plain code `SQLITE_BUSY`, but the connection opens with extended result codes.
10. `RowReader.double()` reads the value before it checks for `NULL`.
11. `PreviewStore.write` reads `errno` after the file calls of `removeDamaged`.

### 3.3 Memory and allocations, measure in M10

1. `PreviewMaker.render` draws a whole child canvas: all strokes, text boxes, and cards, in one command buffer, without a cut to the region. It also builds a whole `FrameRenderer` with a new command queue, library, and pipelines, and an arena for all points. For a D-56 child, one preview took 0.184 s and a peak memory growth of 206 MB (`R-bench-1.xcresult`, `PreviewMakerPerformanceTests`). A restore clears the preview cache (D-97), so after a restore each visible card renders this way. D-157 holds the question.
2. Each `CanvasRenderer` builds its own `InkResources` on the main actor: a command queue, the default library, and about 14 pipeline states. This can be a part of the late frame at the start of the open of an empty card (M10).
3. `giveParentImage` takes the frame lock of both engines on the main actor. The render thread holds that lock for a whole frame, so the main actor can wait for a frame. The comment of `RenderEngine` says that it never waits.
4. `CommittedLayer` makes its build lists new with each layer, so the first build after a rotation or a transition grows them inside a frame. Four lists have no reserve.
5. `GlyphRaster` makes a `CTFont` copy and a `CGContext` for each new glyph. `GlyphAtlas.insert` copies the key list of the page for each new glyph, because `guard var page` shares the buffer. Both run only for a new glyph. SF Mono needs about 95 glyphs per scale.
6. `TextEncoder` looks up the font ID of `TextLayout.baseFont` for each box in each pass. The ID is always 0.
7. `PreviewDecoder` copies its reused buffer into a new array at each decode.
8. `PDFExporter` lays out each text box twice: once for the page bounds and once for the lines. The M8 measures put all text work at about 0.5 s of a 7.5 s export.
9. The close of a canvas does not cancel its export or its preview renders.
10. `SpatialGrid.removeEntry` scans a cell linearly. A first erase of the 1,000 oldest strokes of one cell of 20,000 took 5.96 ms on the Mac.

### 3.4 Tools and tests

1. No run uses Metal API validation. A run of the render suites with `TEST_RUNNER_MTL_DEBUG_LAYER=1` in each milestone finds faults like 1.3.
2. `Scripts/assertion-density.swift` counts the checks of a nested function in the outer function too, and counts each `guard` that returns a value, also `return []`. The five nested functions of today are 5 lines or shorter, so the numbers do not change today.
3. Many contract checks restate the line before them, for example `assert(textures.count == 2)` after a literal of two textures. M10 already plans to read them. The Model reviewer listed 20 such checks in Model, Geometry, and InkEngine, and the Rendering reviewer 12 in Rendering. Each package is at exactly 2.00, so each removed check needs a real one.
4. `RowChannel` ends only with `finish()`. Seven test suites make a canvas and never remove it, so each leaves a consumer task and its library.
5. `StressContent.swift:47` drops an error of `try?` without a handler (SAFE-02).
6. Code without a caller: `navigate(to:camera:)` of the app, `ToolState.isTextEnabled`, `WALCheckpointer.completed`, `StrokeStore.blockListCount`, and several public API of Geometry and Model that only tests use.
7. The PDF writes the strokes and the text boxes in the order of a `Dictionary`, so two exports of one canvas give other bytes.

## 4. Readiness for M9

The code of M8 is ready for M9: `make check` and `make coverage` pass on the branch (section 5). M9 itself is not ready to start. It has no plan, and these parts are missing:

1. Restore in `Persistence`: no `sqlite3_backup_*` wrapper, no check of `integrity_check`, `page_size`, and `user_version` of a picked file, and no close or reopen of the repository. `open` has the precondition `connection == nil`.
2. A test on the Mac showed that the backup API does not call the WAL hook. After a restore, the WAL holds the whole library, so the restore needs its own checkpoint.
3. The clock moves forward only at launch (`AppComposition.makeClock`). `HybridClock` has no operation to move forward to a newer value.
4. `DeviceStateStore` has no API to clear the cameras or the path. `CanvasSessions` has no `removeAll`.
5. `BackupFeature` holds an empty namespace and no tests.
6. storage.md section 7.5 does not clear the preview cache, but D-97 and architecture.md section 6 say that a restore clears it. `PreviewStore.removeAll()` has no caller.
7. No budget exists for "Back up now" or for a restore.

Checked on the Mac with SQLite 3.50.6: a `VACUUM INTO` copy is in rollback journal mode and opens read-only without a `-shm` file. A backup into the live WAL database works while the checkpointer connection is open. A source with another page size fails with `SQLITE_READONLY`, as storage.md says.

The product owner decides D-148 to D-161 in [decisions.md](decisions.md) before the M9 plan.
